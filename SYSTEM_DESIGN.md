# System Design Write-up

## Double-booking prevention

The core guard is not application code — it's a database constraint. `Appointment` has a **partial unique index** on `(doctorId, slotStart)` scoped to `WHERE status IN ('PENDING', 'CONFIRMED')` (migration `20260820150751_partial_unique_active_slot`). Prisma's schema DSL can't express a filtered unique constraint, so this index is hand-written SQL layered on top of the generated schema. A plain `@@unique` would have been wrong: it would permanently lock a slot even after cancellation, since Postgres unique indexes don't distinguish live rows from soft-deleted ones. Scoping the index to only active statuses means a cancelled or completed appointment frees the slot for re-booking, while a live hold or confirmed booking blocks it.

Booking is a straight `INSERT`, not a `SELECT`-then-`INSERT`. That ordering matters: a check-then-insert pattern has a race window between the check and the write where two concurrent requests can both pass the check. Letting the unique index reject the second concurrent insert closes that window — the database, not application logic, is the single source of truth for "is this slot taken." The API layer catches the resulting constraint violation (Prisma's `P2002`, or the raw Postgres `23505` code when the violation comes from a hand-written index Prisma doesn't statically know about — see `src/lib/db-errors.ts`) and returns `409 Conflict`. This was load-tested directly: firing two concurrent booking requests at the same slot reliably returns `201` for one and `409` for the other, with no double-write under load.

## Slot hold mechanism

A booking isn't confirmed the instant a slot is picked — the patient still has to fill in the symptom form. To stop that window from silently blocking a slot from every other patient indefinitely, selecting a slot creates an `Appointment` row with `status = PENDING` and `holdExpiresAt = now + 5 minutes`. That row participates in the same partial unique index as a `CONFIRMED` one, so it blocks the slot for other patients immediately, without waiting for symptom-form submission. If the patient completes the form in time, `POST /appointments/:id/confirm` flips the row to `CONFIRMED` and clears `holdExpiresAt`. If they abandon it, the row simply expires — a cron job (`sweepExpiredHolds`, `GET /api/cron/sweep-holds`) periodically finds `PENDING` rows past their `holdExpiresAt` and flips them to `CANCELLED`, which drops them out of the active-index scope and frees the slot. Expiry is a sweep, not a client-side timer, so it's correct even if the patient closes the tab.

## Doctor leave conflict handling

Marking a doctor on leave for a date is not just a calendar entry — it's a write path that must reach every patient with a live booking on that date. `cancelAppointmentsForLeave` (called synchronously from the leave-creation endpoint, not deferred to a background job) finds every `PENDING`/`CONFIRMED` appointment for that doctor on that date, flips each to `CANCELLED`, and queues a `LEAVE_CONFLICT` notification per affected patient — one `EMAIL` row explaining the reschedule, plus a `CALENDAR` row with `action: "delete"` so both sides' calendar events get torn down (an event created on booking has no reason to survive a cancellation it didn't cause). Doing this synchronously in the request, rather than in a cron sweep, means the admin's UI response itself reports how many bookings were affected — no separate "did it work" check needed.

## Notification failure handling

Every notifiable event (booking confirmation, cancellation, leave conflict, appointment reminder, medication reminder) goes through one write path — `queueNotification` — which inserts a `NotificationLog` row as `PENDING` rather than sending anything inline. Sending happens later, in `processNotificationQueue` (`GET /api/cron/process-notifications`), so a slow or down email/calendar provider never blocks the request that triggered the notification, and every attempt is durably recorded before it's ever attempted. Each row tracks `attempts` and `lastError`; a failed send increments `attempts` and stays `FAILED` (eligible for retry on the next cron tick) until it hits `MAX_NOTIFICATION_ATTEMPTS`, at which point it's marked `ABANDONED` and stops being retried — this was verified directly by running the queue processor with no `RESEND_API_KEY`/Google credentials configured: rows land as `FAILED` with the exact "not configured" reason, not a crash, and the booking flow that triggered them completes unaffected.

The LLM calls follow the same never-block-the-request principle, though the fallback goes one step further: `generatePreVisitSummary`/`generatePostVisitSummary` are wrapped so a *thrown* error (a real Anthropic API failure) returns `{ok: false, error}`, stored as `aiSummaryFailed: true` plus the reason — booking/visit flows complete regardless, exercised directly with a deliberately-broken key. A *missing* key, however, doesn't fail at all: it routes to a local, rule-based engine (`symptom-triage.ts` for pre-visit, `prescription-parser.ts` for post-visit) that produces the same shape of output — urgency/chief-complaint/questions, or a parsed medication schedule with normalized `intervalHours` — with no network call. Every row records which path actually ran via `aiSource: "LLM" | "LOCAL"`, so the UI never mislabels a rule-based result as AI-generated. Medication reminders get scheduled either way, since both paths yield the same structured schedule shape.
